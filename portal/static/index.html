FAIR data

API reference

What is FAIR? Data that is Findable, Accessible, Interoperable and Reusable: described in a standard, machine-readable way, with a lasting identifier, so that people and software (including AI and ML tools) can find it, understand it and use it again. It's the international standard for research data, and what funders such as NIH, Horizon Europe and UKRI ask for.

This page is the review step of a pipeline that runs on the VAST Data Platform. Researchers and HPC jobs write folders of data onto VAST over S3 or NFS; a DataEngine function works out what each file is, drafts a metadata record, and waits here for a person to approve it. Approving publishes standard, machine-readable metadata next to the data.

  1. Upload. A researcher uploads over S3, or an HPC job writes straight into the folder over NFSv4. A _READY file marks the folder complete.
  2. Event. Every new object, or file written over NFSv4, raises an event. The triggers put it on a Kafka topic hosted on VAST.
  3. Profile and curate. DataEngine runs fair-curate for each event. It profiles each data file, and when _READY arrives it drafts a record for the folder.
  4. Record. Facts come from file headers and the researcher's own README and CITATION.cff. The model only proposes descriptive fields. The draft goes to VAST DB and to _fair/record.json in the folder.
  5. Review, here. You accept, edit or reject what was proposed and supply anything missing. Publishing writes your decisions as _fair/review.json, which raises another event.
  6. Publish. The function takes a VAST snapshot of the folder (the published bytes, preserved), writes RO-Crate, Croissant and a landing page next to the data, gives the dataset an identifier, and scores it again. Each file gets an HTTP download link that is served only while the file still matches what was published.
  7. Find. Publishing also indexes the dataset in VAST DB: an embedding in a vector-indexed table (VAST Vector Search) (fair.search) for searching by meaning, and one row per variable (fair.variables) for exact questions such as "every dataset with sea_surface_temperature". Press Enter in the search box, or use Find a variable.
  8. Query. Publishing loads the data itself into VAST DB too, one table per part (fair-db/data): rows of a CSV, cells of a NetCDF grid, cadences of a light curve, variants of a VCF, events and particles of a ROOT file. Each column keeps its reviewed units and meaning. Query the data in place on a published dataset filters it where it is stored, and /id/<ark>/tables/<table> serves the same query over HTTP as CSV, JSON or Parquet. The portal reads them through the VAST DB Python SDK, which a notebook or job can use the same way. For SQL, VAST runs Trino as a managed application on the cluster's own CNodes, so there is no query cluster to set up; this demo doesn't deploy it.
  9. Backlog. Data already on the system is found through VAST Catalog, a periodic snapshot of every file in the namespace. Backlog lists folders that hold data but have no FAIR record (dark data), with size, formats and any docs. Curate drops a _READY marker, and the same function curates the folder in place. The estate bucket fair-estate is shared over S3 and NFS.

A route through the portal with the demo datasets, in about fifteen minutes. Curate is where records are drafted, reviewed and published; Find data is for the people who then look for and use the data. Only steps 2 and 5 change anything: they add a folder or publish a record.

  1. The list. Open Curate. The left column is one list, one line per dataset: Published · FAIR 92, Ready to review, or Dark data · needs licence and creators when publishing waits on a person. Under each value, one line says where it came from: a blue dot for the NetCDF header (title, keywords, instrument), teal for the folder's CITATION.cff (the eight authors, licence, DOI), purple for the model's proposals, with their evidence and how sure it was. Accepted facts are quiet, with a tick. The strip at the top is the FAIR score before and after; FAIR checks, in the tabs below, lists what every point is for (FAIR score).

  5. Publish. On a dataset that is still waiting, accept or edit the highlighted proposals and enter your name.   6. Find it. Switch to Find data. The home page is a search box, a few example sentences, and the numbers: how many datasets, how many rows can be asked in place, how much data stayed where it was written. Type ocean temperature from satellites (ranked by meaning, from the stored embeddings) or a variable such as sea_surface_temperature or Muon_pt; narrow by format, licence, or Queryable.
  7. Ask it. Open Road traffic statistics … Wales. Ask this dataset is the one highlighted thing on the page. Click one of the three suggested questions (they run at once: their queries were checked when the dataset was published) or type average traffic on the M4 by year. On OISST, try average sea temperature between 50 and 60N, 40 to 10W: one figure, with how many rows it covered and how long VAST DataBase took.
  8. The rest of the page. The tabs below hold the facts and citation, the variables with their units, the files with checksums, Use it from code (the same query from Python with the VAST DB SDK, from HTTP, and as SQL for Trino, which this demo doesn't deploy), and similar datasets. Landing page is plain HTML with schema.org metadata embedded; the same address returns RO-Crate to machine clients (Accept: application/ld+json).

Data model lists the VAST DB tables: every record version, who made it and the scores, plus the search index, the variables and the data tables. Production lists what this demo leaves out.

What the model may and may not do

It may propose a title, description, keywords, domain, technique, instrument, coverage and variable meanings. It never proposes creators, licence, publisher or identifiers, because a wrong guess there is worse than none. Its confidence is capped at 0.9, so a guess never looks as sure as a fact.

When you can publish

Publishing needs an accepted title, description, licence and creators; RO-Crate itself requires a licence. Until then the Publish button stays disabled and the panel says what is missing. When you publish, any proposal you left alone is accepted as shown.

Duplicates

If the same files (by checksum) already sit in another folder, the review says so, so a copy is not published twice.

What the pipeline stores, what it embeds for search, and how a record becomes standard metadata.

A record's fields

Every field in a record carries five things: its value, its source (header, companion, inferred, human or none), the evidence (for example oisst.nc#summary or CITATION.cff), a confidence from 0 to 1, and a status (accepted, proposed, rejected or missing). Values from file headers and the researchers' documents are accepted as they are.

Search by meaning

Each published dataset gets one embedding from the embedding model (1024 dimensions), scaled to unit length and stored in a vector-indexed column of fair.search (squared L2 distance, which ranks exactly like cosine similarity on unit vectors). The text embedded is one passage, in this order: title, description, Keywords:, Domain:, technique, instrument, temporal and spatial coverage, then Variables: each name with its description and CF standard name. The passage is cut at 1,200 characters, because some embedding servers reject longer inputs, so the most important text comes first. A query is embedded with a short search instruction in front, as the model expects. Each result's score is its cosine similarity, plus up to 0.10 for query words found in its title, keywords, domain or description. Below 0.35 the portal says there's no strong match.

VAST Vector Search, in VAST DataBase, answers the query. If the Query Engine is unavailable, the portal reads the same stored vectors with a plain select and ranks them itself. Each result says which engine answered.

Find a variable

An exact lookup rather than a semantic one, over fair.variables: name, CF standard name, units and description, case-insensitive, with underscores and spaces treated alike. An exact CF standard-name match ranks first.

Why the dark copies

A self-describing format still says a lot with no documents: the dark NetCDF copy keeps its title, keywords and coverage from its header. A dark CSV or TIFF says almost nothing, so the model can describe it but can't publish it: licence and creators have to come from a person. The duplicate warning also flags each dark copy as the same bytes as its documented twin.

Where the facts come from

Each file's source, checksum and licence evidence, with the attribution it needs, is in data/SOURCES.md in the repository. data/ground_truth.json records what is actually true about each folder, and the accuracy scorecard grades the pipeline's drafts against it.

The FAIR score is computed by fixed rules, not by a model: the same record always gets the same score, and every point traces to one check.

There are 18 checks keyed to the RDA FAIR Data Maturity Model indicators (as the F-UJI assessor reads them), grouped into Findable, Accessible, Interoperable and Reusable. Some count double, such as a persistent identifier or a recognised licence. Each principle's score is the share of its weight that passes; the total is the share overall.

Before and after

  • Before is the folder as it arrived: only what its files and documents already state, with no model and no publishing.
  • On publish is the score once your review is applied and the dataset is published. It updates live as you accept or edit fields.

Some checks can only pass at publish: a persistent identifier, a landing page that outlives the data, a catalog entry, and formal JSON-LD metadata (RO-Crate and Croissant). That is why a well-documented folder still scores well below 100 before publishing.

The checks for the open dataset are listed under FAIR checks on the review screen, with ✓ for passed and ○ for not yet.
